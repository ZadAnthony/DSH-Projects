# Main-session continuity

ProjectStore is the sole durable owner of prepared/current/old carrier relations. The stock-backed Projects factory creates actual Agents and journals; `MainContinuityNative` prepares and retires only the exact root reserved by its attempt. `admission.ts` owns finite input leases and activity epochs; `runtime.ts` joins one evaluation, preparation and publication attempt. No Goal state or reservation is transferred.

`MainContinuityRuntime.onSettledTurn` consumes the plugin driver's real `ProjectTurnSettled` fact after the original normal business turn flushes. It deduplicates the exact creation/start identity. Stop, idle, context refreshes and hidden Bot output do not start evaluations. A newer activity epoch cancels unpublished authority; the original manager still owns its cancellation cleanup and usage settlement before another evaluation uses its slot.

Before manager input reads or evaluation begin, waiting for the main to become idle is cancellable: an expired or superseded attempt releases only its waiter, never stops the main, and lets the next valid normal-turn receipt proceed. Already-started manager/read settlement still joins its original physical owner before the slot is reused.

`MainSessionManager.install` supplies the same dedicated complete prompt, readonly schema and invocation guard for first creation and cold reopening. Each request goes through `stock/request/harness.ts`; only the current evaluation input and its tool continuation seqs are selected. The runtime prepares its bounded `managerInput` directly from the exact durable turn cut: current consumed inputs plus the last outward assistant message of each of up to three normally completed turns. Full new-main history selection is deferred until a valid switch passes the live safety check. The Bot must have an explicit configured provider/model. It cannot silently use a work model or issue business/Memory/configuration writes. See [MANAGER-README.md](MANAGER-README.md).

Preparation uses the exact-attempt `control.createPreparedAgent` creation permit; it never opens general input or resume admission for an unpublished root. Preparation creates no business input. It copies the selected originals' exact image/file bytes from their physical holders into the prepared carrier, then persists a required `projects/history-import` containing canonical `historical-evidence` literals, installs the ordinary current-value request owners, validates the complete preview and flushes. History never enters Inbox, becomes current Memory or replays a quoted tool call. First, continuation and cold requests use the same history fitter and complete-candidate meter; see [history-README.md](history-README.md).

Publication requires the original main's input leases, Inbox and owned native responsibilities to be settled and flushed. `ContinuityPorts.safe` returns a synchronous assertion for the captured responsibility generation; Runtime checks it again inside the short publication slot and Store CAS. Independent execution roots do not count as the main's owned work. Accepted old input and late results retain their original carrier instead of moving to manufacture safety.

Native permission presets, sandbox, approval and plan policy are read from the services owned by the actual selected Agent preset, with the ordinary context owner used only when that preset has no owner. Preparation inherits through those same services and checks effective equality. Pending, wanted or running policy transitions retain the original receiver and prevent publication; inheritance creates no Inbox input.

Store commits retirement and current publication in one CAS. Failed private preparation retains the old current; its physical identity remains recorded until the real retirement owner confirms cleanup. A commit response failure is resolved by rereading the exact Store attempt/header relationship. Unreadable publication outcome closes routing. Stop after a confirmed CAS preserves the durable new current and cancels pending activation. Reopening does not retry old evaluations or replay old work.

Required `projects/main-continuity` facts record evaluation-start, decision and settlement in the same journal. `installContinuityEventSchemas` must be part of the provider's schema initialization before cold reads.

## Verification boundary

`tests/stock-continuity.test.ts` uses actual stock package exports, ProjectStore, the Projects factory/driver, original journals, tools and readonly source readers, with controlled external model responses. It covers dedicated first/cold Harness and current evaluation scope, legal/denied tool continuation, real normal-turn settlement, deduplication and a three-carrier history window, actual original-return delivery state and cancellation before a later evaluation. `tests/stock-continuity-relay.test.ts` additionally uses the normal private facade and actual configured preset, native todo tool, staged file upload, responsibility owner and Store CAS to publish three physical main carriers, including a fresh-facade cold reopen and new business input. It confirms that an independent running execution root does not block the main, exact historical file bytes survive in each prepared namespace, historical messages stay out of Inbox and the old native tool executes once. Normal tgz installation and browser interaction remain with full host acceptance. Model understanding and actual usage effects remain unverified.
